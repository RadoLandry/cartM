## Summary

Add a size and fit intelligence layer to CartMind's knowledge graph. The feature provides: (1) a per-category size chart model that maps body attributes to size labels with merchant-override support, (2) a cross-product size mapping table that enables deterministic cart conflict detection, (3) a `getSizeRecommendation` function for the conversational AI and cart widget to query, (4) a `detectSizeConflicts` function for the cart intelligence engine, and (5) a "Size Charts" admin tab in the existing knowledge-graph route for merchant curation. Return-data feedback is modelled but deferred to Phase 5 integration.

## Technical Context

**Language/Version**: TypeScript 5.x  
**Primary Dependencies**: React Router 7, `@shopify/shopify-app-react-router`, Polaris, Prisma, PostgreSQL  
**Storage**: PostgreSQL via Prisma — three new models: `SizeChart`, `CrossSizeMapping`, `SizeReturnRecord`  
**Testing**: Vitest for unit and integration tests in `tests/unit/knowledge-graph` and `tests/integration/routes`  
**Target Platform**: Shopify embedded admin app on Vercel serverless; cart widget storefront  
**Project Type**: Web service / Shopify app feature extension  
**Performance Goals**: Size recommendation and conflict detection calls must complete in-process under 50 ms (pure table lookup, no AI inference); admin tab load under 300 ms p95  
**Constraints**: Must preserve Shopify-first admin patterns (Polaris + App Bridge), validate all route action inputs at the boundary, avoid over-fetching Shopify GraphQL (no new Shopify API calls required for this feature), strict TypeScript, merchant overrides must survive catalog re-syncs  
**Scale/Scope**: Up to 10k products per merchant; size charts cover ~10 category tags; cross-size mappings expected to be O(50) rows per shop

### Planning Assumptions

- `ProductVariant.sizeCategory` values are migrated to the controlled vocabulary defined in [data-model.md](./data-model.md) as part of this feature.
- Default size charts (boxing gloves oz, apparel S/M/L/XL, shorts waist) are seeded via a script rather than auto-generated by LLM for the first implementation.
- The `CustomerProfile` model (PRD-defined) is not yet in the schema; size profile data for logged-in customers will be stored in the existing `sizeProfile` JSON field once `CustomerProfile` is added. For this feature slice, recommendations use only anonymous session-scoped size data passed in the request.
- No new Shopify webhook handlers are required; the feature reads from data already synced by the catalog ingestion pipeline.

## Phase 0: Research Output

Research decisions are captured in [research.md](./research.md) and resolve the main planning questions:

1. **Size chart structure**: JSON breakpoints in a single `SizeChart` row per `(shop, categoryTag, sizeSystem)`. Merchant override is a separate JSON field in the same row so syncs never touch it.
2. **Conflict detection approach**: Explicit `CrossSizeMapping` table with pairwise category-size entries. Purely rules-based — deterministic and unit-testable. Severity (WARNING/ERROR) is encoded per mapping pair.
3. **Size recommendation algorithm**: Three-step resolution — profile → chart breakpoint lookup → null. Merchant `overrideBreakpoints` take precedence over auto-generated breakpoints.
4. **Return data**: Separate `SizeReturnRecord` table. Batch adjustment job gated on minimum sample count. Merchant overrides are never touched by adjustment logic.
5. **Admin surface**: Extend the existing Polaris knowledge-graph route with a Size Charts tab; no new top-level route for v1.
6. **Customer size profile**: Stored in the `sizeProfile` JSON field of the existing (planned) `CustomerProfile` model; anonymous users use session-scoped data only.
