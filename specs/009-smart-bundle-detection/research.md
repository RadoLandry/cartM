# Research: Smart Bundle Detection

## Bundle persistence strategy

### Decision
Add first-class Prisma persistence for bundle rules and bundle rule components, following the existing `KitDefinition` and `KitRequirement` pattern instead of storing bundle logic in route-local JSON blobs or function metafields.

### Rationale
The repository already uses Prisma-backed merchant configuration for adjacent merchandising features such as kit completeness, size mappings, and color compatibility. There is no current `BundleRule` model in `prisma/schema.prisma`, and there is no existing bundle engine file in `app/lib/cart-intelligence`, so a real persisted model is required to make bundle matching, admin CRUD, and future function projection auditable and reusable.

### Alternatives considered
- Store bundle definitions only in Shopify metafields: rejected because admin CRUD, preview, and deterministic cart analysis would become harder to type, validate, and test locally.
- Store bundle rules as freeform JSON in a single table: rejected because component-level quantities, status, and prioritization need relational structure to stay maintainable.

## Matching and scoring model

### Decision
Use deterministic bundle coverage scoring based on required component satisfaction and quantity fulfillment. Emit explicit statuses for `qualified`, `nearly_complete`, `partial`, and `not_applicable`, with `nearly_complete` driven by rule coverage and merchant-configured completion thresholds.

### Rationale
The feature spec requires both full qualification and near-complete prompts. The existing `detectKitCompleteness` slice already demonstrates a predictable “coverage plus ordered missing requirements” pattern; extending that design to bundles keeps the logic understandable, low-noise, and easy to unit test.

### Alternatives considered
- Binary matching only: rejected because the PRD explicitly requires prompting shoppers to complete bundles when they are close.
- Heuristic or AI-assisted bundle inference: rejected because request-time analysis must remain deterministic and fast.

## Overlapping bundle behavior

### Decision
Return all legitimate bundle opportunities, but classify overlaps explicitly so downstream consumers can distinguish between compatible parallel opportunities and competing offers that draw from the same qualifying items.

### Rationale
The feature spec requires the system to detect multiple bundles while also avoiding misleading double-promotion. A competition flag on match results preserves transparency for cart and checkout consumers without forcing the matcher to decide presentation policy alone.

### Alternatives considered
- Always collapse to a single “best” bundle: rejected because merchants may want multiple valid opportunities visible in different surfaces.
- Ignore overlap entirely: rejected because it would produce shopper messaging that implies incompatible discounts can stack.

## Completion suggestions and availability

### Decision
Build completion guidance from missing rule components, enriched with currently purchasable product and variant candidates derived from `Product`, `ProductVariant`, and product-relationship evidence. Suppress completion prompts when the required path is not purchasable.

### Rationale
The feature spec explicitly forbids promoting completion paths that cannot currently be bought. Existing `ProductVariant.inventoryQuantity` and synced catalog data provide enough evidence to decide whether a suggested next step is actionable.

### Alternatives considered
- Emit only missing component labels with no purchasability signal: rejected because downstream UI could not distinguish actionable from informational prompts.
- Compute availability entirely in the storefront: rejected because it would duplicate business logic and increase drift across consumers.

## Merchant control surface

### Decision
Add a dedicated Polaris route for bundle rule management rather than placing bundle CRUD inside the existing knowledge-graph route.

### Rationale
`app/routes/app.knowledge-graph.tsx` already combines taxonomy, colorway, and size tooling. Bundle rules are a separate merchandising concern with their own create/edit/preview flow, and the PRD already anticipates a standalone Bundle Rule Manager surface.

### Alternatives considered
- Extend the knowledge-graph route with another tab: rejected because the page is already broad and would become harder to navigate and test.
- Delay admin UI and seed rules only through scripts: rejected because merchant control is part of the feature scope.

## Shopify Function alignment

### Decision
Define a compact active-rule projection contract generated by the app backend for future discount and cart-transform consumers, but keep bundle eligibility matching authoritative in the app layer.

### Rationale
The PRD’s function constraints are strict: no Node APIs, no external calls, and tight CPU limits. Precomputing a compact representation of active bundle rules lets future functions stay self-contained while the richer matcher and admin logic remain in the main app.

### Alternatives considered
- Recompute full bundle matching inside the function runtime: rejected because it risks exceeding runtime and payload constraints.
- Couple the app matcher output directly to one function implementation: rejected because the contract needs to serve cart UI, checkout, and function consumers independently.
